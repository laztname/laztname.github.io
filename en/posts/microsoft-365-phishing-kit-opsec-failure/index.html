Microsoft 365 Phishing Kit: Source Code Exposed by an OPSEC Failure

28-10-2026
Cyber Security, Offensive, Defensive

Introduction

That morning, as usual, I started working through incoming Security Operations tickets. One of them was related to a suspected phishing email that had just been moved to quarantine by Microsoft Defender for Office 365 (MDO).

MDO already has built-in mechanisms to detect and remediate malicious emails. However, in practice, I have encountered several cases where phishing emails still managed to reach users’ inboxes before eventually being detected and moved to quarantine.

What’s more interesting is that this sometimes happens with a batch of emails sharing similar patterns, from the sender and subject line to their threat indicators. For example, out of 20 similar phishing emails, 18 were successfully blocked, while the remaining 2 somehow managed to reach users’ inboxes.

My team and I had previously opened a ticket with Microsoft to ask about this behavior. Based on the response and handling we experienced, this behavior appeared to be related to the expected detection and email processing mechanisms rather than necessarily indicating a system failure. Of course, the exact cause still depends on the investigation results and the details of each case.

This ticket was where the investigation began. Initially, it looked like a routine phishing email investigation. However, after I started tracing the link embedded in the email, I stumbled upon something much more interesting behind the phishing infrastructure.

After reviewing the available indicators, I was confident that the ticket was a true positive. I then submitted the IOC (Indicator of Compromise) to Microsoft Defender for Endpoint (MDE) and the firewall as part of the mitigation process.

Out of curiosity, I decided to open the link and discovered that it redirected to another domain. The redirect process also appeared to collect browser fingerprints or visitor metadata, potentially to distinguish legitimate users from bots and security crawlers.

This technique is commonly used to evade automated detection, allowing security systems to see a different page from the actual phishing page served to intended victims.

Reusing an Old Domain for Phishing Infrastructure

After checking the domain history through archive.org, I found indications that the domain used in the phishing email was an old domain that may have been abandoned by its previous owner and later registered again by the threat actor.

Cases like this are interesting because an old domain does not necessarily mean it is still owned by the same party. Threat actors can take advantage of expired domains to establish infrastructure with an existing domain history, making it appear more trustworthy than a newly registered domain.

This can be particularly relevant because defenders commonly apply deny-by-default policies or stricter controls to NRDs (Newly Registered Domains).

This type of phishing technique is quite common. To bypass email security gateways, the link embedded in the email uses an old domain. Once the user accesses it, the redirector forwards them to a newly registered domain hosting the actual phishing page.

Since phishing pages are frequently flagged as malicious by browsers and security services, threat actors also tend to register multiple domains to maintain their infrastructure.

In the context of email security, domain age is only one of several parameters used to determine whether an email is legitimate or malicious. An old domain that has changed ownership may slip past detection rules that focus primarily on newly registered domains.

Taking a Closer Look at the Phishing Login Page

After following the redirect chain, I landed on a login page impersonating Microsoft. At this point, I became curious about how the phishing kit actually worked, particularly how the page processed the victim’s username and password.

By inspecting the HTML source rendered in the browser, I found clues indicating that the application used PHP on the server side and had a directory named api.

I then tried to inspect that directory and discovered that directory listing was enabled. This meant the server was exposing a list of files and folders inside the directory instead of restricting access or displaying an appropriate page.

From the exposed file listing, I found several clues suggesting that this phishing kit was not exclusively targeting Microsoft 365 accounts. There were also indications of GoDaddy support, along with mechanisms that appeared to identify corporate email addresses and determine which organizations were being targeted.

Directory Listing: The Beginning of an OPSEC Failure

The exposed directory listing made me even more curious about how well the threat actor had secured their infrastructure. If an internal directory could be accessed publicly, there was a possibility that other files that should never have been publicly available were exposed as well.

To test this hypothesis, I examined publicly accessible files and directories using ffuf, a web fuzzing tool. The goal was to understand the extent of the exposure rather than simply collect directory names.

While waiting for the process to complete, I also tried guessing filenames that might be available. Since the api directory was already visible in the browser, I suspected there might be an archive named api.zip left behind on the server.

And that guess turned out to be correct.

The api.zip file was accessible without authentication. After inspecting the archive, I discovered that it contained the source code used by the phishing kit.

This was where the investigation became much more interesting. A simple configuration mistake had potentially exposed far more information than what was visible from the phishing login page itself.

Source Code, Admin Panel, and Default Credentials

By reviewing the exposed source code, I was able to understand more about the application’s structure and identify clues about the location of its administrative panel. One file that caught my attention was login.php, which revealed information about the panel’s authentication mechanism.

During the inspection, I found indications of default credentials being used. This is a fairly basic security issue, especially when the administrative panel is accessible from the internet without additional access restrictions.

The combination of exposed source code and weak authentication configurations can significantly increase the risk of administrative panel compromise. In this case, the threat actor behind the phishing kit had potentially left behind a weakness that could be exploited by someone else.

After that, I discovered a dashboard displaying several components of the phishing kit’s management system.

From the dashboard, client list, activity logs, and settings page, it became clear that this application was not just a standalone fake login page. There was an entire management component behind it, used to manage targets or clients, record activities, and modify system configurations.

Exposed Infrastructure Leads to Threat Actor Profiling

While examining the Settings page further, I discovered several insecure configurations. One of them involved secret values displayed through placeholders on the configuration page. Since these values were still accessible from the browser side, sensitive information such as API keys could potentially be exposed.

From the configuration, I identified several API keys associated with third-party services, including WHM and Cloudflare.

After identifying the API keys, I attempted to perform API calls to understand the level of access granted by each credential. One particularly interesting finding was the access provided through the Cloudflare API.

Based on the results, the exposed credentials allowed access to domain information registered under the Cloudflare account, including the ability to view and manage DNS configurations such as A records. I also discovered information about the email address used as the account owner.

I then used this information as a pivot for OSINT investigation into the identified username and email address. I searched across several OSINT platforms and other publicly available sources.

During the process, I discovered a GitHub account with a username associated with the identified identity. However, the account had already been disabled. There were also some indications of connections to other platforms, although further verification was limited due to access restrictions and API limitations on the services I used.

To further validate the finding, I attempted to create an email draft in Gmail and examined the information returned in Gmail’s response.

WHM API Exposure and Server Access

Apart from Cloudflare, I also discovered configurations related to WHM (WebHost Manager). Based on the findings, the exposed API provided access to several administrative operations on the server.

During testing in an authorized environment, I found that this access could be used to create new users with administrative privileges. Through these accounts, further server access could be obtained, including terminal access via SSH.

Since the access was valid, I attempted to add myself as an administrator through the API and register an SSH key on the threat actor’s server.

After gaining access to the server, I discovered several databases that were interesting enough to investigate further.

These findings show that investigating a phishing kit does not have to stop at the phishing page visible to victims. By looking deeper into its configurations, API integrations, and supporting infrastructure, we can gain a much broader understanding of how the phishing campaign is managed.

Beyond revealing the internal components of the phishing infrastructure, exposed credentials and account information can also serve as pivots for threat actor profiling through OSINT.

Ultimately, this case demonstrates how misconfigurations within a phishing kit can expose more than just a fake login page. They can also reveal sensitive information and internal infrastructure components behind the operation.

Indicators of Compromise (IoCs)

As part of the infrastructure investigation, I further analyzed the information obtained from the exposed Cloudflare account. From this analysis, I was able to identify several domains registered under and associated with the Cloudflare account.

These domains provide additional leads for understanding the infrastructure used in the phishing activity being investigated.

Final Thoughts

One interesting takeaway from this investigation is that threat actors operating phishing infrastructure can still make fundamental OPSEC mistakes. From exposed directory listings and publicly downloadable source code to default credentials on administrative panels and secret API keys exposed through dashboard settings, these findings show that even seemingly complex attack infrastructure is not necessarily managed with good security practices.

From a defender’s perspective, this case is a reminder that detecting phishing emails is only one part of the process. We also need to understand how links work, follow redirect chains, identify relevant IOCs, and ensure those indicators are properly handled through available security controls. Additionally, we should never assume that a domain is safe simply because it has existed for a long time. Its ownership history and usage context also need to be considered.

From a red team perspective, these findings provide another valuable lesson. OPSEC is not just about hiding identities or building infrastructure that looks convincing. Server configurations, credential management, access restrictions, and sensitive file handling are equally important. A single overlooked mistake can expose information that should never have been publicly accessible.

Ultimately, both defenders and red teamers can take away the same lesson: security is not only determined by how well a system withstands attacks, but also by how carefully we manage the small details that are often overlooked.

It is worth emphasizing that this investigation focuses on observing and analyzing the exposed infrastructure. I did not take down the infrastructure or attempt to take over the system. The objective was to understand how the phishing kit worked, identify the visible OPSEC weaknesses, and draw lessons that can be applied to defensive security and authorized security testing.
